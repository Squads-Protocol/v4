# V4.5 Revised: Upgrade Guide for Squads Multisig 4r

This guide tells integrators what to change when they move from Squads v4 to
Squads Multisig 4r ("version 4, revised"). It covers TypeScript clients, Rust clients,
on-chain programs that call Squads through CPI, and CLI users.

For the full list of repository changes, see [CHANGELOG.md](CHANGELOG.md).

## 1. Summary

- **4r is a new program.** The v4 program `SQDS4ep65T869zMMBKyuUq6aD6EgTu8psMjkvj52pCf` has no
  upgrade authority. It cannot change. 4r is deployed at
  `SMS4Rd3C3P1V2PdGRSdZCVQ5fPJk7NsV7vAVoUgSvT5`.
- **All PDAs are different.** The program ID is an input to every PDA. A v4 multisig, its vaults
  and its transactions do not exist on 4r.
- **The wire format does not change.** Account layouts, instruction arguments, account order,
  discriminators and custom error codes are byte-for-byte the same as v4. 4r adds fifteen
  instructions (`log_event`, `multisig_create_from`, `multisig_create_from_v3`, six
  `multisig_migrate_*` and six `multisig_migrate_v3_*`) and seven error codes (6045 to 6051).
- **4r has an on-chain move from v4 and from v3.** A v4 vault transaction (or a v3 transaction)
  creates the 4r "successor" of a multisig and moves assets and authorities to it. The v4 (or v3)
  members approve each step (section 11).
- **4r can emit events.** They are opt-in: a client adds one extra account. Clients that do not
  add it see no change (section 12).
- **The SDKs are new packages with new APIs.** The TypeScript SDK moves from web3.js v1 and Solita
  to `@solana/kit` and Codama. In Rust, the program crate has a core layer (types, builders, PDAs,
  messages) that does not depend on Anchor. Clients and other programs import only that core.
- **One program behavior changes.** A `spending_limit_use` SPL transfer from a vault token account
  to the same token account now fails with Anchor error 2040.
- **The old packages are frozen.** Use them only for the v4 program.

| Component | v4 (frozen) | 4r (new) |
|---|---|---|
| Program ID | `SQDS4ep65T869zMMBKyuUq6aD6EgTu8psMjkvj52pCf` | `SMS4Rd3C3P1V2PdGRSdZCVQ5fPJk7NsV7vAVoUgSvT5` |
| Program crate | `squads-multisig-program` 2.0.x | `squads-multisig-4r-program` 0.1.0 |
| Rust SDK | `squads-multisig` 2.1.x | `squads-multisig-4r` 0.1.0 |
| TypeScript SDK | `@sqds/multisig` 2.1.x | `@sqds/multisig-4r` 0.1.0 |
| CLI | `squads-multisig-cli` 0.1.x | `squads-multisig-4r-cli` 0.1.0 |
| Anchor | 0.32 | 1.2.1 |
| Solana crates | 2.x | 4.x (Agave 4.3) |
| IDL | legacy format, in `sdk/multisig/idl` | spec 0.1.0, `idl/squads_multisig_4r_program.json`, Program Metadata |

The 0.x versions are for the audit and formal verification period. Version 1.0.0 follows the
mainnet release. The 0.x APIs can change before 1.0.0.

## 3. Program identity and accounts

### 3.1 Program IDs

| Build | Program ID | Use |
|---|---|---|
| Mainnet (default build) | `SMS4Rd3C3P1V2PdGRSdZCVQ5fPJk7NsV7vAVoUgSvT5` | Production |
| `testing` feature | `GyhGAqjokLwF9UXdQ2dR5Zwiup242j4mX4J1tSMKyAmD` | Local validator tests |

All SDK functions use the mainnet ID by default. Each function accepts a different program ID for
local or staging deployments:

- TypeScript: `{ programAddress }` as the last argument.
- Rust builders, PDA and message helpers: `program_id: Option<&Address>`.

### 3.2 PDAs

The seeds do not change. The program ID changes, so every derived address changes.

| PDA | Seeds |
|---|---|
| Program config | `"multisig"`, `"program_config"` |
| Multisig | `"multisig"`, `"multisig"`, `create_key` |
| Vault | `"multisig"`, `multisig`, `"vault"`, `vault_index: u8` |
| Transaction | `"multisig"`, `multisig`, `"transaction"`, `transaction_index: u64 LE` |
| Proposal | `"multisig"`, `multisig`, `"transaction"`, `transaction_index: u64 LE`, `"proposal"` |
| Batch transaction | `"multisig"`, `multisig`, `"transaction"`, `batch_index: u64 LE`, `"batch_transaction"`, `transaction_index: u32 LE` |
| Ephemeral signer | `"multisig"`, `transaction`, `"ephemeral_signer"`, `index: u8` |
| Spending limit | `"multisig"`, `multisig`, `"spending_limit"`, `create_key` |
| Transaction buffer | `"multisig"`, `multisig`, `"transaction_buffer"`, `creator`, `buffer_index: u8` |

Do these steps:

1. Derive every PDA with the 4r program ID. Do not use a cached v4 address.
2. Store the program ID next to each multisig address in your database. The same `create_key`
   gives a different multisig address on each program.
3. Do not send funds to a vault address that you derived with the wrong program ID. The funds stay
   in an account that the other program cannot sign for.

### 3.3 Check the account owner

v4 and 4r accounts have the same discriminators and the same layout. A decoder that does not
check the owner reads a v4 account as a 4r account, and the opposite. This can make your
application trust an account from the wrong program.

Do these steps:

- Always compare the account owner with the expected program ID before you decode.
- In TypeScript, use `fetch*Checked` or `decodeChecked`. The generated `fetch*` and `decode*`
  functions do not check the owner or the discriminator.
- In Rust, use `squads_multisig_4r::rpc::fetch_*`, `rpc::decode_checked`, or the core
  `account::decode_checked`. A plain borsh decode does not check the owner.
- In on-chain programs, use the core `account::decode_checked` (any framework), or Anchor
  `Account<'info, T>` with the 4r program crate.

## 4. What does not change

The golden tests (`programs/squads_multisig_program/tests/golden_wire_format.rs` and the SDK
fixture tests) decode and encode real mainnet v4 accounts and instructions with the 4r types. All
bytes agree. These items are the same in v4 and 4r:

- The 9 account types: `Multisig`, `ProgramConfig`, `Proposal`, `VaultTransaction`,
  `ConfigTransaction`, `Batch`, `VaultBatchTransaction`, `SpendingLimit`, `TransactionBuffer`.
  The fields, field order, sizes and 8-byte discriminators are the same.
- The 36 instructions, with the same names, 8-byte discriminators and argument layouts.
- The account list of each instruction: the order, the `writable` and `signer` flags, and the
  optional accounts.
- Optional accounts. When you omit an optional account, you pass the program ID in its place. In
  4r this is the 4r program ID.
- Custom errors 6000 to 6044, with the same names and messages.
- The vault `TransactionMessage` byte format for `vault_transaction_create` and
  `batch_add_transaction`.
- `multisig_create` (v1) is still deprecated. It fails with `MultisigCreateDeprecated` (6044).
  Use `multisig_create_v2`.
- Without the opt-in event account, the program emits no events, as v4 (section 12).

If your application has its own decoders or instruction encoders, add the 4r program ID. The
byte layouts stay the same.

## 5. Program behavior changes

### 5.1 `spending_limit_use`: SPL transfer to the same token account fails

Anchor 1.x rejects an instruction when two mutable typed accounts have the same address.

| Case | v4 | 4r |
|---|---|---|
| SPL: `vault_token_account == destination_token_account` | Succeeds. Moves no tokens. Decreases `remaining_amount`. | Fails with Anchor error **2040** `ConstraintDuplicateMutableAccount` |
| SOL: `destination == vault` | Succeeds. Decreases `remaining_amount`. | Same as v4 |

What to do:

- Do not send an SPL spending limit transfer from a vault to its own token account. It has no
  useful result.
- If your code catches errors from `spending_limit_use`, handle error 2040.
- If you used this transfer to decrease `remaining_amount` on purpose, use the SOL path, or remove
  and add the spending limit again.

No other instruction is affected. The Anchor check covers only mutable `Account` and
`InterfaceAccount` fields that are not `init`. Only `spending_limit_use` has two such fields that
one address can fill.

### 5.2 New Anchor framework error codes

Anchor 1.2 adds error codes 2040 to 2044. It does not renumber existing codes. In this program, only
2040 can occur (see 5.1). If you map Anchor error numbers to messages, add 2040.

### 5.3 Runtime error text

Agave 4.x changes the text of some runtime errors. Examples are signature verification failures
and heap access violations. These errors come from the validator, not from the program. Do not
compare error strings. Use the error code, or the custom program error number.

### 5.4 Fewer program logs

4r writes fewer log lines than v4. Use events (section 12) instead of log lines.

- There is no `Program log: Instruction: <Name>` line. The program is built with Anchor's
  `no-log-ix-name` feature. Read the instruction name from the instruction data or from events.
- These v4 lines are removed: `transaction index: N` (`vault_transaction_create`,
  `config_transaction_create`), `batch index: N` (`batch_create`, `batch_add_transaction`),
  `batch size: N`, `Creation fee: N`, and the `token_program … mint … vault … destination …`
  line of the `spending_limit_use` SPL path.
- Effect: about 100 compute units less for each instruction. The SPL path of `spending_limit_use`
  uses 61% fewer compute units (48,846 to 19,031 in the local test), because it does not format
  four addresses as base58.
- Anchor error logs (`AnchorError … Error Code: …`) do not change.

### 5.5 Changes that do not need action

- **Account growth.** `Multisig` and `Proposal` reallocation now sets new bytes to zero. The stored
  data is the same, because the program writes the full account after it grows.
- **Compute units.** The program is built for SBPF v3. Each instruction uses 0.1% to 0.6% fewer
  compute units than the same instruction on SBPF v0. Your compute unit limits stay correct.
- **`security.txt`.** The name is "Squads Multisig 4r Program". The 4r audit status is "pending".

### 5.6 Verify the deployed program

The verifiable build uses SBPF v3. Use these arguments:

```sh
solana-verify build --base-image solanafoundation/solana-verifiable-build:4.3.0 --arch v3 \
  --library-name squads_multisig_4r_program
solana-verify get-program-hash -u <cluster url> SMS4Rd3C3P1V2PdGRSdZCVQ5fPJk7NsV7vAVoUgSvT5
```

## 6. IDL changes

| Item | v4 | 4r |
|---|---|---|
| File | `sdk/multisig/idl/squads_multisig_program.json` | `idl/squads_multisig_4r_program.json` |
| Format | Legacy Anchor IDL (before 0.30) | Anchor IDL spec 0.1.0 |
| Program name | `squads_multisig_program` | `squads_multisig_4r_program` |
| On-chain location | Legacy Anchor IDL account | Program Metadata program |
| PDA seeds and fixed addresses | Not included | Included |
| Order of accounts and types | Source order | Alphabetical |

What to do:

- Tools that read only the legacy format cannot read the 4r IDL. Examples are Solita and
  `@coral-xyz/anchor` before 0.30. Use Codama, Anchor 0.30 or later, or the 4r SDKs.
- Look up IDL entries by name, not by array index. The order changed.
- `anchor idl fetch` from Anchor 1.x reads the IDL from Program Metadata. `Program.fetchIdl` in
  `@coral-xyz/anchor` reads the legacy IDL account, which 4r does not have. Load the IDL from the
  repository file, or use the 4r SDK.
- The `TransactionMessage`, `CompiledInstruction` and `MessageAddressTableLookup` types are not in
  the Anchor IDL. They use 1-byte and 2-byte length prefixes that the IDL cannot express. The
  TypeScript client adds them, and the Rust core defines them. To build `transaction_message`
  bytes, use the SDK helper (see 7.5 and 8.4).
- The unused `Vote` type is not in the IDL.
- New in 4r: the `log_event` instruction, its `LogEventArgs` type and the error
  `ProtectedInstruction` (6045). The event types are not in the IDL (section 12).
- New in 4r: the `multisig_create_from` instruction, the six `multisig_migrate_*` instructions
  (one for each asset class), the type `TokenAuthorityKind`, and the errors 6046 to 6050
  (section 11).
- New in 4r: the `multisig_create_from_v3` instruction, the six `multisig_migrate_v3_*`
  instructions, their argument types, and the error 6051 (section 11.7).
- In Anchor TypeScript, the workspace name changes from `SquadsMultisigProgram` to
  `SquadsMultisig4rProgram`.

## 7. TypeScript: `@sqds/multisig` to `@sqds/multisig-4r`

### 7.1 Install

```sh
npm uninstall @sqds/multisig   # only if you do not also operate v4 multisigs
npm install @sqds/multisig-4r @solana/kit
```

- `@solana/kit` ^8.4.0 is a peer dependency.
- Node.js 20.18 or later.
- The package has ESM and CommonJS builds.
- `@solana/web3.js` v1 is not a dependency.

You can keep `@sqds/multisig` and `@sqds/multisig-4r` in one application. Use each package only
for its own program.

### 7.3 Type changes

| Value | v4 | 4r |
|---|---|---|
| Address | `PublicKey` | `Address` (a base58 string type). Use `address("...")` |
| `u64`, `i64` (`transactionIndex`, `amount`, timestamps) | `beet.bignum` (`BN` or `number`) | `bigint` when decoded. `number \| bigint` as input |
| `u8`, `u16`, `u32` | `number` | `number` |
| `Option<T>` when decoded (`rentCollector`, `memo`) | `T \| null` | `Option<T>`. Use `unwrapOption`, `isSome` from `@solana/kit` |
| `Option<T>` as input | `T \| null` | `T \| null`, or `some(x)` / `none()` |
| Signer accounts (`creator`, `member`, `rentPayer`, `createKey`) | `PublicKey` | `TransactionSigner`. Use `createNoopSigner(address)` if a wallet signs later |
| Byte arrays | `Buffer` / `Uint8Array` | `ReadonlyUint8Array` |
| Accounts | Solita class instances (`.pretty()`, `.serialize()`) | Plain objects. Encode with `get*Encoder()` |
| Enums with data (`ProposalStatus`, `ConfigAction`) | `{ __kind: "Approved", timestamp }` | Same shape. Numbers are `bigint` |
| `Period` | Numeric enum | Numeric enum |

`Permissions` has no helper class. Use these helpers. They match the v4 `Permission` values:

```ts
import type { Permissions } from "@sqds/multisig-4r";

export const Permission = { Initiate: 1, Vote: 2, Execute: 4 } as const;
export type Permission = (typeof Permission)[keyof typeof Permission];

export const permissions = (...granted: Permission[]): Permissions => ({
  mask: granted.reduce<number>((mask, p) => mask | p, 0),
});
export const hasPermission = ({ mask }: Permissions, p: Permission) => (mask & p) === p;
```

Read a multisig:

```ts
import { address, createSolanaRpc, unwrapOption } from "@solana/kit";
import { fetchMultisigChecked } from "@sqds/multisig-4r";

const rpc = createSolanaRpc("https://api.mainnet-beta.solana.com");
const { data } = await fetchMultisigChecked(rpc, address("<multisig>"));
const nextIndex = data.transactionIndex + 1n; // bigint, not BN
const rentCollector = unwrapOption(data.rentCollector); // Address | null
```

### 7.4 Instruction builders

The v4 helpers in `instructions.*` took a `multisigPda` and a `transactionIndex`. They derived the
PDAs, used `creator` as the default `rentPayer`, and serialized the message. The 4r builders are
generated. They take each account and each argument as a flat input:

- You derive the PDAs (`transaction`, `proposal`, `vault`) yourself.
- You give `rentPayer` explicitly.
- Arguments that were in `{ args: { ... } }` are now fields of the same input object.
- `memo` and other `Option` arguments are required. Use `null` for "none".
- `get*InstructionAsync` variants exist where the IDL gives PDA defaults: `multisigCreateV2`
  (derives `multisig` and `programConfig`) and the `programConfig*` instructions.

Before (v4):

```ts
const ix = multisig.instructions.vaultTransactionCreate({
  multisigPda, transactionIndex, creator, vaultIndex: 0, ephemeralSigners: 0,
  transactionMessage: new TransactionMessage({ payerKey: vaultPda, recentBlockhash, instructions: [transferIx] }),
});
```

After (4r):

```ts
import { getTransferSolInstruction } from "@solana-program/system";
import { createNoopSigner } from "@solana/kit";
import {
  fetchMultisigChecked, findProposalPda, findTransactionPda, findVaultPda,
  getProposalApproveInstruction, getProposalCreateInstruction,
  getTransactionMessageBytes, getVaultTransactionCreateInstruction,
} from "@sqds/multisig-4r";

const { data } = await fetchMultisigChecked(rpc, multisig);
const transactionIndex = data.transactionIndex + 1n;
const [vault] = await findVaultPda({ multisig, index: 0 });
const [transaction] = await findTransactionPda({ multisig, index: transactionIndex });
const [proposal] = await findProposalPda({ multisig, transactionIndex });

// The vault signs the inner instruction through the program, so use a no-op signer.
const transfer = getTransferSolInstruction({
  source: createNoopSigner(vault), destination: recipient, amount: 1_000_000n,
});

const instructions = [
  getVaultTransactionCreateInstruction({
    multisig, transaction, creator: member, rentPayer: member,
    vaultIndex: 0, ephemeralSigners: 0, memo: null,
    transactionMessage: getTransactionMessageBytes({ vault, instructions: [transfer] }),
  }),
  getProposalCreateInstruction({ multisig, proposal, creator: member, rentPayer: member, transactionIndex, draft: false }),
  getProposalApproveInstruction({ multisig, member, proposal, memo: null }),
];
```

Note the seed names: `findTransactionPda` takes `index`, but `findProposalPda` takes
`transactionIndex`.

### 7.5 Vault transaction messages and execution

- `getTransactionMessageBytes({ vault, instructions, addressLookupTables })` replaces
  `transactionMessageToMultisigTransactionMessageBytes`. It takes Kit `Instruction` objects, not a
  web3.js `TransactionMessage`. It needs no blockhash and no payer.
- Address lookup tables are a record: `{ [tableAddress]: addressesInTableOrder }`. The helper
  drops tables that supply no account.
- The output is byte-identical to the Rust client.

v4 `instructions.vaultTransactionExecute` read the `VaultTransaction` and the lookup tables
through a `Connection`. In 4r you read them and give them to the helper:

```ts
import { fetchAddressLookupTable } from "@solana-program/address-lookup-table";
import { fetchVaultTransactionChecked, getVaultTransactionExecuteInstructionWithAccounts } from "@sqds/multisig-4r";

const { data: vaultTransaction } = await fetchVaultTransactionChecked(rpc, transaction);
const addressLookupTables = Object.fromEntries(
  await Promise.all(
    vaultTransaction.message.addressTableLookups.map(async ({ accountKey }) => {
      const table = await fetchAddressLookupTable(rpc, accountKey);
      return [accountKey, table.data.addresses] as const;
    }),
  ),
);
const execute = await getVaultTransactionExecuteInstructionWithAccounts({
  multisig, proposal, transaction, member,
  message: vaultTransaction.message,
  vaultIndex: vaultTransaction.vaultIndex,
  addressLookupTables,
});
```

For `batchExecuteTransaction`, call `getAccountsForExecute(...)` and add the result to
`instruction.accounts`.

### 7.6 Send transactions

The v4 `rpc.*` and `transactions.*` modules do not exist in 4r. Build and send with Kit:

```ts
import {
  appendTransactionMessageInstructions, createTransactionMessage, pipe,
  sendAndConfirmTransactionFactory, setTransactionMessageFeePayerSigner,
  setTransactionMessageLifetimeUsingBlockhash, signTransactionMessageWithSigners,
} from "@solana/kit";

const sendAndConfirm = sendAndConfirmTransactionFactory({ rpc, rpcSubscriptions });
const { value: blockhash } = await rpc.getLatestBlockhash().send();
const message = pipe(
  createTransactionMessage({ version: 0 }),
  (m) => setTransactionMessageFeePayerSigner(feePayer, m),
  (m) => setTransactionMessageLifetimeUsingBlockhash(blockhash, m),
  (m) => appendTransactionMessageInstructions(instructions, m),
);
await sendAndConfirm(await signTransactionMessageWithSigners(message), { commitment: "confirmed" });
```

### 7.8 Find program accounts

```ts
import { getBase58Decoder, type Base58EncodedBytes } from "@solana/kit";
import { getMultisigDecoder, MULTISIG_DISCRIMINATOR, SQUADS_MULTISIG4R_PROGRAM_ADDRESS } from "@sqds/multisig-4r";

const accounts = await rpc
  .getProgramAccounts(SQUADS_MULTISIG4R_PROGRAM_ADDRESS, {
    encoding: "base64",
    filters: [{
      memcmp: {
        offset: 0n,
        bytes: getBase58Decoder().decode(MULTISIG_DISCRIMINATOR) as Base58EncodedBytes,
        encoding: "base58",
      },
    }],
  })
  .send();
const multisigs = accounts.map(({ pubkey, account }) => ({
  address: pubkey,
  data: getMultisigDecoder().decode(Buffer.from(account.data[0], "base64")),
}));
```

The query is scoped to the 4r program, so the owner is correct. Field offsets for `memcmp`
filters are the same as in v4.

### 7.9 Applications that keep web3.js v1

You can use the 4r SDK in a web3.js v1 application. Use `@solana/compat` to convert values:
`fromLegacyPublicKey`, `fromLegacyKeypair` and `fromLegacyTransactionInstruction`. Keep the
4r instructions in Kit form when you can. Each conversion is a place where an account role can
change by mistake.

## 8. Rust clients: `squads-multisig` to `squads-multisig-4r`

### 8.1 Two crates, no Anchor

The 4r types and builders live in the program crate itself, in a **core** layer that does not need
Anchor. The Anchor program is the crate's default `program` feature. Pick one dependency:

```toml
[dependencies]
# Core only: types, builders, PDAs, messages, decoding. Host and SBF.
squads-multisig-4r-program = { version = "0.1.0", default-features = false }

# Or: the same core, re-exported, plus async RPC fetches (feature `fetch`, on by default).
squads-multisig-4r = "0.1.0"
```

| Item | v4 | 4r |
|---|---|---|
| Address type | `anchor_lang::prelude::Pubkey` (solana-pubkey 2.x) | `solana_address::Address` |
| Instruction type | `solana_program::instruction::Instruction` 2.x | `solana_instruction::Instruction` |
| Anchor | Required (re-exported) | Not used by the core or by `squads-multisig-4r` |
| Core dependencies | the whole program dependency tree | `borsh`, `solana-address`, `solana-instruction`, `thiserror` |
| Borsh | 0.10 (`try_to_vec()`) | 1.x (`borsh::to_vec(&value)`) |
| RPC client | `solana-rpc-client` 2.2 | `solana-rpc-client` 4.3 (`squads-multisig-4r`, feature `fetch`) |
| Errors | `thiserror` 1 | `thiserror` 2 |
| Rust version | (Solana 2.2 minimum) | 1.97.1 or later with feature `fetch` (Agave 4.3 crates) |

The 4r types unify with the Solana 3.x crate line and later:

- `solana-pubkey` 3.x and 4.x `Pubkey` is the same type as `Address`.
- `solana-instruction` 3.5 and later is the same type as 4.x.
- Solana 2.x types (`solana-sdk` 2.x, `solana-pubkey` 2.x) do not unify. Upgrade to the 3.x line
  or later. If you are on 3.x, run `cargo update -p solana-address -p solana-instruction`.
- `rpc::fetch_*` take `&solana_rpc_client::nonblocking::rpc_client::RpcClient` from 4.3. A client
  from another major version is a different type.

The paths below use `squads_multisig_4r`. With only the core, use `squads_multisig_4r_program`:
the module names are the same, except `rpc`.

### 8.4 Example: propose, approve and execute

```rust
use squads_multisig_4r::builders::{
    ProposalApprove, ProposalCreate, VaultTransactionCreate, VaultTransactionExecute,
    SYSTEM_PROGRAM_ID,
};
use squads_multisig_4r::instructions::{ProposalCreateArgs, ProposalVoteArgs, VaultTransactionCreateArgs};
use squads_multisig_4r::message::{transaction_message_bytes, vault_transaction_execute};
use squads_multisig_4r::pda::{get_proposal_pda, get_transaction_pda, get_vault_pda};
use squads_multisig_4r::rpc::{fetch_multisig, fetch_vault_transaction};

let transaction_index = fetch_multisig(&rpc, &multisig, None).await?.transaction_index + 1;
let (vault, _) = get_vault_pda(&multisig, 0, None);
let (transaction, _) = get_transaction_pda(&multisig, transaction_index, None);
let (proposal, _) = get_proposal_pda(&multisig, transaction_index, None);
let transfer = solana_system_interface::instruction::transfer(&vault, &recipient, 1_000_000);

let propose = [
    VaultTransactionCreate {
        multisig, transaction, creator: member, rent_payer: member,
        system_program: SYSTEM_PROGRAM_ID,
    }
    .instruction(
        VaultTransactionCreateArgs {
            vault_index: 0,
            ephemeral_signers: 0,
            transaction_message: transaction_message_bytes(&vault, &[transfer], &[])?,
            memo: None,
        },
        None,
    )?,
    ProposalCreate {
        multisig, proposal, creator: member, rent_payer: member,
        system_program: SYSTEM_PROGRAM_ID,
    }
    .instruction(ProposalCreateArgs { transaction_index, draft: false }, None)?,
    ProposalApprove { multisig, member, proposal }
        .instruction(ProposalVoteArgs { memo: None }, None)?,
];

// Later, after the proposal is approved:
let vault_transaction = fetch_vault_transaction(&rpc, &transaction, None).await?;
let execute = vault_transaction_execute(
    &VaultTransactionExecute { multisig, proposal, transaction, member },
    vault_transaction.vault_index,
    vault_transaction.ephemeral_signer_bumps.len() as u8,
    &vault_transaction.message,
    &address_lookup_tables, // every table that the message uses
    None,
)?;
```

- Builders with arguments return `Result<Instruction, CoreError>`. Builders without arguments
  return `Instruction`.
- `vault_transaction_execute` emits the lookup table accounts in message order. You can give a
  superset of tables. It returns `MissingAddressLookupTable` if a table is missing.

### 8.5 Program ID and optional accounts

Every builder, PDA helper and message helper takes `program_id: Option<&Address>`. `None` means
the mainnet program. For a local or staging program, give its ID:

```rust
let ix = ConfigTransactionExecute { multisig, member, proposal, transaction, rent_payer: None, system_program: None }
    .instruction(Some(&staging_program_id));
```

An omitted optional account (`None`) is encoded as the program ID that you give. Anchor reads an
optional account as `None` only when its address is the program that runs.

The frozen v4 program has the same account and instruction layout. To read v4 accounts or build v4
instructions with the 4r core, pass `Some(&LEGACY_V4_PROGRAM_ID)` (`SQDS4…`) to every builder,
PDA helper, message helper and decoder. A missed argument falls back to the 4r ID without an error.

## 9. On-chain programs (CPI)

### 9.1 Program ID checks

If your program compares an account owner or a program account with `SQDS4…`, add
`SMS4Rd3C3P1V2PdGRSdZCVQ5fPJk7NsV7vAVoUgSvT5`. Decide for each check if your program accepts v4,
4r, or both. Keep the owner check. The account layouts are the same, so the owner is the only
difference between a v4 account and a 4r account.

If your program derives Squads PDAs (for example a vault address), derive them with the 4r
program ID. `pda::*` works on-chain; it uses the runtime syscall.

### 9.2 CPI without Anchor (recommended)

Use the core. It builds for SBF, it works with any framework (Anchor of any version, Pinocchio,
plain `solana-program`), and it adds no Anchor dependency to your program:

```toml
[dependencies]
squads-multisig-4r-program = { version = "0.1.0", default-features = false }
```

```rust
use squads_multisig_4r_program::{builders, instructions::ProposalVoteArgs, pda};

let (proposal, _) = pda::get_proposal_pda(multisig.key, transaction_index, None);
let approve = builders::ProposalApprove { multisig: *multisig.key, member: *member.key, proposal }
    .instruction(ProposalVoteArgs { memo: None }, None)
    .map_err(|_| ProgramError::InvalidArgument)?;
solana_cpi::invoke_signed(&approve, &[multisig.clone(), member.clone(), proposal_info.clone()], signer_seeds)?;
```

- Read Squads accounts with `account::decode_checked` (owner and discriminator check).
- The builders put `program_id` (default: the mainnet ID) in the instruction. For a local test
  build, pass the test program ID.

### 9.3 CPI with the Anchor program crate (Anchor 1.2)

If your program uses Anchor 1.2, you can also use the Anchor-generated CPI module:

```toml
[dependencies]
anchor-lang = { version = "1.2.1", default-features = false, features = ["solana-v4"] }
squads-multisig-4r-program = { version = "0.1.0", features = ["cpi"] }
```

Anchor 1.2 has two Solana feature sets: `solana-v3` (the default) and `solana-v4`. They cannot be
enabled together. The 4r program crate enables `solana-v4`. Set `default-features = false` on
`anchor-lang` and on `anchor-spl` (if you use it), or the build fails with a compile error.

Changes from `squads-multisig-program` with Anchor 0.32:

- The crate is `squads_multisig_4r_program`. The CPI module is
  `squads_multisig_4r_program::cpi`, and the account structs are in
  `squads_multisig_4r_program::cpi::accounts`.
- Your program must use Anchor 1.2. The CPI types come from `anchor-lang` 1.2.
- `CpiContext::new` and `CpiContext::new_with_signer` take the program ID (`Pubkey`), not the
  program `AccountInfo`:

  ```rust
  // v4, Anchor 0.32
  let ctx = CpiContext::new(ctx.accounts.squads_program.to_account_info(), accounts);
  // 4r, Anchor 1.2
  let ctx = CpiContext::new(squads_multisig_4r_program::ID, accounts);
  ```

- `Context` has one lifetime: `Context<'info, T>` replaces `Context<'_, '_, 'info, 'info, T>`.
- In `#[derive(Accounts)]`, Anchor 1.x deprecates `AccountInfo`. Use `UncheckedAccount<'info>`
  (with a `/// CHECK:` comment) or `Program<'info, SquadsMultisig4rProgram>`.
- Borsh 1.x: replace `value.try_to_vec()?` with `borsh::to_vec(&value)?`. This applies to
  `TransactionMessage` too.
- The v4 SDK helper `squads_multisig::cpi::create_multisig` is gone. Call
  `squads_multisig_4r_program::cpi::multisig_create_v2(ctx, MultisigCreateArgsV2 { .. })`, or use
  `builders::MultisigCreateV2` (9.2).
- The program entrypoint and the `custom-heap` allocator are compiled only into the 4r program
  itself. With the `cpi` feature, they do not affect your program. Do not use `no-entrypoint`
  with the default features: the default `custom-entrypoint` feature then adds the 4r entrypoint
  to your crate.

## 11. Move a multisig from v4 or v3 to 4r

4r has seven instructions for the move from v4: `multisig_create_from`, and one
`multisig_migrate_*` instruction for each asset class. A v4 vault transaction calls them through
CPI. Thus the v4 members approve each step, with the v4 threshold and time lock. The move from v3
has seven matching instructions (section 11.7). The move gives no power to another party: each step
needs a signature that only the source program gives, after the source approvals. After the move,
the assets also depend on the 4r upgrade authority (`MIGRATION_SAFETY.md` section 9.8). Sections
11.1 to 11.6 describe the move from v4; section 11.8 is for teams that announce a migration.
`MIGRATION_SAFETY.md` gives the safety argument.

### 11.1 The successor

The successor of a v4 multisig is the 4r multisig with `create_key` = the v4 multisig address:

```
successor = PDA_4r("multisig", "multisig", v4_multisig)
vault i   = PDA_4r("multisig", successor, "vault", i)
```

- Only `multisig_create_from` can create the successor. `multisig_create_v2` needs a `create_key`
  that signs. The v4 multisig address is a v4 PDA, and v4 never signs for it.
- Each v4 multisig has one successor. You can calculate the address before the account exists.
  Assets that you send to a successor vault before its creation are safe: only the v4 members can
  create the successor.
- Do not use the v4 `create_key` again as a 4r `create_key`. Its keypair can still exist. Then
  another person can create a multisig at that address first.
- The successor stores the v4 multisig address in `create_key`. Thus a client can find the source
  of a successor.

| Client | Successor address |
|---|---|
| TypeScript | `findSuccessorPda({ sourceMultisig })` |
| Rust core | `migration::get_successor_pda(&v4_multisig, None)` |

### 11.2 `multisig_create_from`

- **Signer.** A vault of the v4 multisig (`source_vault`, any index). 4r checks the v4 owner, the
  `Multisig` discriminator, and the vault PDA with the v4 program ID.
- **Config.** 4r copies the members, permissions, threshold, time lock, config authority and rent
  collector from the v4 account when the transaction executes. `transaction_index` starts at 0.
  4r does not copy spending limits.
- **Vault hints.** The v4 `config_authority` or `rent_collector` can be a vault of the same v4
  multisig. Then give its index in `config_authority_vault_index` or `rent_collector_vault_index`.
  4r uses the successor vault with the same index. A hint that does not match fails with
  `MigrationInvalidVaultHint` (6047).
- **Payment.** The v4 vault pays the rent and the 4r creation fee. The program reads the fee when
  the instruction executes, so the members approve a cap: `max_creation_fee`. A larger fee fails
  with `MigrationCreationFeeTooHigh` (6050). The planners set the cap to the fee at planning time.
- **Once.** A second call fails, because the account exists.
- **Event.** `MultisigCreate`, with `creator` = the v4 vault.

### 11.3 The migrate instructions

Each migrate instruction moves one asset class. Thus one call can reach only the programs of its
class, and a reviewer reads one kind of change in each batch entry.

| Instruction | Arguments after the prefix | Fixed accounts | Accounts for each item | Action |
|---|---|---|---|---|
| `multisig_migrate_sol` | `keep`, `memo` | System program | none | System transfer of the balance minus `keep` |
| `multisig_migrate_tokens` | `close_source`, `memo` | token program, ATA program, System program | source token account, mint, destination ATA | Create the ATA of the successor vault (idempotent), `transfer_checked` of the whole balance, optional close of the source |
| `multisig_migrate_token_authorities` | `items`, `memo` | token program | the token account or the mint | Token `SetAuthority`, or the Token-2022 metadata `UpdateAuthority` |
| `multisig_migrate_stakes` | `memo` | clock sysvar, Stake program | stake account | Stake `Authorize` staker and withdrawer; Stake `SetLockup` for the lockup custodian |
| `multisig_migrate_vote_accounts` | `memo` | clock sysvar, Vote program | vote account | Vote `Authorize` withdrawer |
| `multisig_migrate_programs` | `memo` | BPF Loader Upgradeable | program data account | Loader-v3 `SetAuthority` |

Rules for all six instructions:

- **Signer.** The same check as `multisig_create_from`. The successor must exist (Anchor error
  3012).
- **Governance.** The successor must have the same members (keys and permissions), threshold, time
  lock and config authority (with the hint) as the v4 multisig at execution. If not, the call fails
  with `MigrationGovernanceMismatch` (6046). The rent collector is not compared.
- **Destination.** The successor vault with the same index as the v4 vault. The program calculates
  it. The instructions have no destination argument.
- **Arguments.** Each argument list starts with `vault_index` and `config_authority_vault_index`.
- **Items.** The items are the remaining accounts, then the optional event account. An account
  count that does not divide into items fails with `MigrationInvalidAssetAccounts` (6048). At most
  64 items in one call (`InvalidInstructionArgs`, 6040).
- **Token program.** One token program (Token or Token-2022) for each call. Another program fails
  with Anchor error 3008.

Tokens always move the whole balance at execution. The v4 vault pays the rent of a new ATA. A
close of the source occurs only when `close_source` is set, the source has no withheld transfer
fees, and the v4 vault can close it. The rent goes to the successor vault. For SOL, `keep` must be
0 or at least the rent minimum (`MigrationInvalidAmount`, 6049).

`TokenAuthorityKind` has 19 values: the 18 Token-2022 `AuthorityType` values in the same order,
then `MetadataUpdate`. Token supports `MintTokens`, `FreezeAccount`, `AccountOwner` and
`CloseAccount`. Before each change, the program reads the current holder from the base fields, the
extension, or the token metadata. `AccountOwner` is only for token accounts that are not an ATA
and have no `ImmutableOwner` extension.

Only the withdrawer of a vote account moves. The withdrawer controls the account, and the members
can set the vote account's authorized voter later with a 4r vault transaction. (The authorized
voter is a role of the Vote program, not a multisig member with the Vote permission.) Changes of
the authorized voter have per-epoch rules that could block a v4 batch.

The lockup custodian of a stake moves with Stake `SetLockup`. The Stake program needs the
custodian to sign while a lockup is in force, and the withdrawer to sign at other times. The
successor cannot sign, so the order depends on the lockup:

| The v4 vault is the custodian, and the lockup is… | Order |
|---|---|
| in force | The withdrawer moves first (the vault signs as custodian to bypass the lockup), then the custodian |
| not in force, and the vault is the withdrawer | The custodian moves first (signed as withdrawer), then the withdrawer |
| not in force, and another party is the withdrawer | The custodian is skipped (`NotAuthority`). It has no power until the withdrawer sets a new lockup |

The authority changes use the unchecked instructions, because the new authority cannot sign
during v4 execution. This is safe, because the program calculates the new authority.

**Skips.** When there is nothing to move, the instruction skips the item and does not fail. The
`Migration` event records the class (`scope`) and one outcome for each item (three for a stake:
staker, withdrawer and lockup custodian).

| Skip reason | When |
|---|---|
| `Empty` | The amount is 0 |
| `Missing` | The account or the extension does not exist, or the account is of another program |
| `NotAuthority` | The v4 vault does not hold the authority, for example after an earlier move |
| `Frozen` | The source or destination token account is frozen |
| `Locked` | A stake lockup is in force, so the withdrawer cannot change |
| `Unsupported` | Transfer hook, non-transferable or paused mint; `AccountOwner` of an ATA |

**Cost.** Measured on the local validator for the whole v4 execute transaction, with events:

| Batch entry | Compute units |
|---|---|
| `multisig_create_from` | 40,741 |
| 1 Token-2022 token (new ATA, source closed) | 78,906 |
| 3 Token tokens (1 moved, 1 frozen, 1 empty and closed) | 86,922 |
| 2 token authorities (1 moved, 1 skipped) | 42,351 |
| 8 Token-2022 authorities (5 moved, 3 skipped) | 74,109 |
| 2 stakes | 76,959 |
| 1 vote account | 43,721 |
| 1 program | 54,177 |
| SOL | 38,990 |

**Limit.** The governance check finds drift. It does not stop a 4r vault transaction that the
members approved earlier on the successor: v4 and 4r execute stale approved vault transactions.

### 11.4 Steps

1. Read the v4 multisig. If its config authority or rent collector is one of its own vaults,
   note the index.
2. On v4, create, approve and execute a vault transaction with `multisig_create_from`. You can add
   a first migrate instruction to the same transaction.
3. List the assets of each v4 vault: SOL, token accounts (Token and Token-2022), the authorities of
   token accounts and mints, stake accounts, vote accounts, and programs that the vault can
   upgrade.
4. On v4, create one batch with one migrate instruction in each batch transaction. The members
   vote once for the whole batch.
5. Execute the batch transactions in order. A failed batch transaction blocks the ones after it.
   Simulate each one first. If one cannot execute, cancel the proposal (`proposal_cancel_v2`) and
   make a new batch with the remaining assets. Assets that moved stay moved.
6. Create the spending limits again on 4r. Update allow lists, treasury settings and off-chain
   records. If a v4 vault was the authorized voter of a vote account (a Vote program role), assign
   a new authorized voter from the successor.
7. On v4, remove the spending limits and close old transaction accounts. Later deposits to the v4
   vaults can move with the migrate instructions again.

While you migrate, change the config on both multisigs, or on neither. A change on one side stops
the migrate instructions until the two are equal again.

| Client | Instructions |
|---|---|
| TypeScript | `getMultisigCreateFromInstructionAsync`; `getMigrateSolInstruction`, `getMigrateTokensInstruction`, `getMigrateTokenAuthoritiesInstruction`, `getMigrateStakesInstruction`, `getMigrateVoteAccountsInstruction`, `getMigrateProgramsInstruction` (they add the item accounts) |
| Rust core | `builders::MultisigCreateFrom::new(..)`; `builders::MigrationAccounts::new(..)`, then `MultisigMigrateSol`, `MultisigMigrateTokens`, `MultisigMigrateTokenAuthorities`, `MultisigMigrateStakes`, `MultisigMigrateVoteAccounts` or `MultisigMigratePrograms` `::new(..).instruction(args, &items, ..)`. Preflight with `migration::mirror` and `migration::check_same_governance` |

### 11.5 The planner, lookup tables and the CLI

The planner does steps 1 to 5 for one v4 vault. It reads the chain and sends nothing.

1. **Inventory.** It finds the SOL, the token accounts (Token and Token-2022), the stake accounts
   (staker, withdrawer or lockup custodian), the vote accounts (withdrawer), the programs (upgrade authority) and the
   mints where the vault is the mint or freeze authority. For these mints, it also reads the
   Token-2022 extension and metadata authorities that the vault holds. It also finds token
   accounts of any owner where the vault is the close authority or the delegate. The scans need
   `getProgramAccounts`. If the RPC refuses a scan, the plan gives a warning. You can turn the
   scans off.
2. **Limit of the mint scan.** A mint where the vault holds only an extension or metadata
   authority is not found. Give such mints in `extraMints` (CLI: `--extra-mint`).
3. **Groups.** Tokens (Token, then Token-2022), token authorities (Token, then Token-2022), stakes,
   vote accounts, programs, then SOL last. The v4 vault pays the rent of the new token accounts
   first. Frozen token accounts are left out with a note. With
   `preserveTokenAccountAddresses`, token accounts that are not an ATA move by owner change and
   keep their address. A close authority that the vault holds moves with `CloseAccount` on the
   accounts of other owners and on the accounts that move by owner change. A delegate role
   cannot move; the plan gives a note.
4. **Batch items.** Each item is a part of one group: the planner never puts two classes in one
   batch transaction. It adds items while three limits hold: 800 message bytes, 30 message accounts,
   and 64 instructions in the execute transaction. The planner counts the worst case for the
   instructions: 9 for each token (a pre-funded ATA address makes the ATA creation longer), 3 for
   each stake, 1 for other items, and 5 for the transaction. Without lookup tables, one item holds
   5 tokens. With lookup tables, the account limit is 52, and one item holds 6 tokens.
5. **Checks.** It finds the vault hints, creates `multisig_create_from` if the successor does not
   exist, compares the governance if it exists, and warns when the v4 vault has too little SOL for
   the new token accounts. The member report (`memberReport`) lists members that only a program
   can sign for (off-curve keys), and warns when the wallet members cannot reach the threshold
   alone. It never stops the plan.
6. **Proposals.** It builds the v4 vault transaction (successor) and the v4 batch (assets), and the
   execute instructions after approval.

**Lookup tables.** A lookup table holds the item accounts, so each vault message is smaller and
each item can hold more accounts. The tables are not frozen: after the batch runs, deactivate them
and close them about 513 slots later to get the rent back.

1. `getMigrationLookupTableAddresses(plan)` gives the accounts (no signers, no programs).
2. `getCreateLookupTablesTransactions` creates and extends the tables (256 addresses for each
   table, 20 for each extend transaction). Wait one slot before you use them.
3. `withMigrationLookupTables(plan, tables)` makes the batch items again with the tables.
4. Compile each execute transaction as a v0 message with the same tables.

The TypeScript and Rust planners use the same rules. Their tests check that they give the same
batch items.

| Client | Functions |
|---|---|
| TypeScript | `planV4Migration`, `withMigrationLookupTables`, `getMigrationLookupTableAddresses`, `getV4MigrationProposal`, `getV4VaultTransactionExecuteInstruction`, `getV4BatchExecuteInstructions`; parts: `getV4VaultInventory`, `inventoryGroups`, `chunkMigrationGroups`, `parseMintAuthorities`, `migrationInstructionTrace`; tables: `getCreateLookupTablesTransactions`, `getDeactivateLookupTableInstruction`, `getCloseLookupTableInstruction` |
| Rust (`squads-multisig-4r`, feature `fetch`) | `planner::plan_v4_migration`, `with_migration_lookup_tables`, `migration_lookup_table_addresses`, `v4_migration_proposal`, `v4_batch_lookup_tables`, `v4_vault_transaction_execute_instruction`, `v4_batch_execute_instructions`; parts: `fetch_v4_vault_inventory`, `inventory_groups`, `chunk_migration_groups`, `parse_mint_authorities`, `migration_instruction_trace`; tables: `lookup_tables::{create_lookup_tables, deactivate_lookup_table, close_lookup_table}` |

CLI, for a v4 member:

```sh
squads-multisig-4r-cli migrate-plan --multisig-pubkey <v4 multisig> [--vault-index 0]
squads-multisig-4r-cli migrate-propose --multisig-pubkey <v4 multisig> --keypair <member> [--approve] [--lookup-tables]
# Other members approve each printed index on v4:
squads-multisig-4r-cli proposal-vote --program-id SQDS4ep65T869zMMBKyuUq6aD6EgTu8psMjkvj52pCf \
  --multisig-pubkey <v4 multisig> --keypair <member> --transaction-index <index> --action approve
# After the threshold approves:
squads-multisig-4r-cli migrate-execute --multisig-pubkey <v4 multisig> --keypair <member> --transaction-index <index>
# With --lookup-tables, after the batch runs:
squads-multisig-4r-cli migrate-lookup-tables --tables <table,...> --keypair <member> --deactivate
squads-multisig-4r-cli migrate-lookup-tables --tables <table,...> --keypair <member> --close
```

- `migrate-propose` prints the v4 transaction indexes: the successor creation first, then the
  batch. Execute them in that order.
- `migrate-propose --lookup-tables` creates the tables before the proposals. The member is the
  table authority, and the payer pays the rent. The command prints the table addresses.
- `migrate-execute` reads the lookup tables from the batch messages. It sends one transaction for
  each remaining batch entry, in order, and stops at the first failure. Run it again after you fix
  the cause, or cancel the proposal and propose again.
- `--keep-token-accounts` keeps the v4 token accounts open. `--preserve-token-account-addresses`
  moves token accounts that are not an ATA by owner change. `--extra-mint` adds a mint to the
  inventory. `--skip-program-scans` turns off the token role, stake, vote, program and mint scans. `--yes`
  skips the confirmation.
- The migrate commands read at `confirmed` commitment.

### 11.6 Assets that the migrate instructions do not move

Move these with a normal v4 vault transaction to the successor vault. Check the destination with
`findSuccessorPda`:

- tokens with a transfer hook, non-transferable tokens, tokens of a paused mint, and frozen token
  accounts
- programs of loader v4: its `TransferAuthority` needs a signature of the new authority, and the
  successor vault cannot sign during v4 execution
- durable nonce accounts (`AuthorizeNonceAccount` does not need the new authority to sign)
- the authorized voter of a vote account (after the move, the successor sets it)
- the delegate role on token accounts of other owners (only the owner can change it), and the
  update authority of a Token-2022 token group
- Token-2022 confidential balances. The public balance moves; with `close_source`, a source token
  account that still has a confidential balance stays open
- NFT metadata authorities, positions in other protocols, and domain names

### 11.7 Move a multisig from v3

4r also moves a Squads v3 multisig (Squads MPL). The rules of sections 11.1 to 11.6 apply, with
these differences. `MIGRATION_SAFETY.md` section 11 gives the safety argument.

- **Successor.** The 4r multisig with `create_key` = the v3 multisig address
  (`findSuccessorPda({ sourceMultisig })`, as for v4). v3 signs as its multisig only in CPIs to
  itself, so only `multisig_create_from_v3` can create it.
- **Signer.** A v3 authority, `authority_index` 1 to 256, in a v3 transaction that the v3 members
  approved. Authority `N` moves to the successor vault `N - 1`: the v3 default vault (1) moves to
  the 4r default vault (0). Other indexes fail with `MigrationInvalidAuthorityIndex` (6051).
- **Config.** Every v3 member gets Initiate, Vote and Execute (v3 has no permissions). The
  threshold stays. There is no time lock, no config authority and no rent collector. Set a rent
  collector later with a 4r config transaction. Set a time lock only after the last move: the
  check requires the time lock of v3, which is 0.
- **Instructions.** `multisig_create_from_v3` and `multisig_migrate_v3_{sol, tokens,
  token_authorities, stakes, vote_accounts, programs}`. Their arguments start with
  `authority_index`; they have no vault hints.
- **Roles delegates.** A v3 member can be a delegate of the v3 roles program. Only that program can
  sign for it, so it can never sign in 4r. `planV3Migration` stops with `V3DelegateMembersError`
  and lists each delegate and its wallet. Before you migrate, replace each delegate with its wallet
  in a v3 transaction of authority 0 (`add_member`, `remove_member`), and check the threshold.
- **Steps.** `planV3Migration`, then `getV3MigrationProposal`: one v3 transaction with the creation
  first, then one migrate instruction per item, SOL last. The members approve it once. Then
  `getV3ExecuteInstructions` gives one `execute_instruction` call per item, in order. A v3
  transaction holds at most 255 instructions.
- **Not movable.** Assets at the v3 multisig address itself or at authority 0, and authorities
  above 256.
- **CLI.** The commands of section 11.5 find the lineage from the owner of `--multisig-pubkey`.
  Use `--authority-index` (default 1) for v3; `--vault-index` is for v4 only. `migrate-propose`
  sends the v3 transaction (`--approve` adds the vote of the member), and `migrate-execute`
  runs the remaining instructions in order. The CLI has no lookup tables for v3.

### 11.8 Before you announce a migration

A public announcement gives an attacker no new power. The design has no secret: the successor
address, the plan and every proposal are public before and after the announcement. An attacker
who knows all of them can still not:

- create the successor first, or with another governance (only the source multisig can create it,
  and it can never sign as the `create_key`);
- run a migrate instruction (it needs a signature that only the source program gives, after the
  source approvals);
- send an asset to another address (the program calculates every destination);
- move an asset while the successor governance differs from the source (every move checks it).

An attacker can send assets to the successor addresses, or freeze a token account if it already
holds the freeze authority. Neither takes an asset.

The remaining risk is the same as for any multisig transaction: members who approve a harmful
proposal. A public migration can bring fake proposals and fake websites. Before you approve:

1. Each instruction of the proposal calls the 4r program `SMS4Rd3C3P1V2PdGRSdZCVQ5fPJk7NsV7vAVoUgSvT5`
   and is `multisig_create_from(_v3)` or `multisig_migrate(_v3)_*`. Reject any other instruction.
2. The successor is `findSuccessorPda({ sourceMultisig })` of your own multisig.
3. `max_creation_fee` is the fee that you expect.
4. Make the plan yourself (SDK or CLI) and compare it with the proposal.

The migration is as secure as the source multisig: the wallets that can approve on v3 or v4 are
the wallets that can approve on the successor.


## 12. Events (new in 4r)

v4 has no events. Indexers must compare account states, and a closed account loses its history.
4r emits events as inner instructions.

### 12.1 How it works

- The program calls its own `log_event` instruction through a CPI. The `Multisig` PDA signs it.
  For the program config instructions, the `ProgramConfig` PDA signs it.
- The instruction data is `log_event` discriminator + `u32` length + borsh `MultisigEvent`.
- The runtime records inner instructions in the transaction metadata. It does not truncate them.
  Program logs can be truncated.
- `log_event` accepts only a signer that the program owns and that is a `Multisig` or
  `ProgramConfig` account. Only the program can sign for these PDAs. A vault transaction that
  calls `log_event` fails with `ProtectedInstruction` (6045). Thus, an event is always real.

### 12.2 Enable events

Events are opt-in. Add the program ID as one read-only account at the end of the instruction,
after all remaining accounts. Without this account, the program emits nothing and works as in v4.

| Client | How |
|---|---|
| Rust core | `builders::with_events(instruction)` |
| `@sqds/multisig-4r` | `withEvents(instruction)` |
| CLI | On by default |
| Other clients | Append `{ address: <program ID>, readonly, not signer }` |

Rules:

- Apply it last. For `vault_transaction_execute` and `batch_execute_transaction`, add it after
  the lookup tables and message accounts.
- Encode omitted optional accounts as the program ID (all SDKs do this). If you leave out the
  optional accounts completely, Anchor reads the event account as one of them, and no event goes
  out.
- `with_events` does nothing for `LEGACY_V4_PROGRAM_ID`. The v4 program has no events.

### 12.3 Events per instruction

| Instruction | Events |
|---|---|
| `program_config_*` | `ProgramConfig` |
| `multisig_create_v2` | `MultisigCreate` |
| `multisig_add_member`, `multisig_remove_member`, `multisig_set_time_lock`, `multisig_change_threshold`, `multisig_set_rent_collector` | `MultisigConfig` |
| `multisig_set_config_authority` | `ConfigAuthorityChange` |
| `multisig_add_spending_limit`, `multisig_remove_spending_limit` | `SpendingLimit` (Add, Remove) |
| `config_transaction_create`, `vault_transaction_create`, `vault_transaction_create_from_buffer`, `batch_create` | `Transaction` (Create) |
| `config_transaction_execute` | `MultisigConfig`, `SpendingLimit` for each spending limit action, `Transaction` (Execute), `Proposal` (Execute) |
| `vault_transaction_execute` | `Transaction` (Execute), `Proposal` (Execute) |
| `batch_add_transaction` | `BatchTransaction` (Add) |
| `batch_execute_transaction` | `BatchTransaction` (Execute); `Proposal` (Execute) after the last transaction |
| `proposal_create`, `proposal_activate`, `proposal_approve`, `proposal_reject`, `proposal_cancel`, `proposal_cancel_v2` | `Proposal` |
| `spending_limit_use` | `SpendingLimitUse` |
| `multisig_create_from`, `multisig_create_from_v3` | `MultisigCreate` (the `creator` is the v4 vault or the v3 authority) |
| `multisig_migrate_*`, `multisig_migrate_v3_*` | `Migration` (`scope` = the asset class; `source` = the lineage and the source vault index; `vault_index` = the successor vault; one outcome for each item, three for a stake) |
| `*_accounts_close`, `vault_batch_transaction_account_close` | `Transaction` or `BatchTransaction` (Close), `Proposal` (Close) |
| `transaction_buffer_*` | None |

Events carry snapshots of the changed accounts (`Option` fields; in Rust, `Option<Cow<_>>`, and
decoding gives owned values). Create events carry the full
transaction. Execute and Close events do not. If an event is longer than the 10 KiB CPI data
limit, all its snapshots are `None`. This occurs for a multisig with about 300 or more members,
or a vault transaction made from a large buffer.

### 12.4 Decode events

1. Get the transaction with its metadata (`getTransaction`, `maxSupportedTransactionVersion: 0`).
2. For each inner instruction, resolve the program ID with the account keys and the loaded
   addresses.
3. Keep only inner instructions to the 4r program ID.
4. Decode the data with the verified decoder: `events::decode_verified_log_event` (Rust) or
   `decodeVerifiedLogEvent` (TypeScript). It returns `None` / `null` for other instructions. It
   fails if the signer of the inner instruction is not the multisig (or program config) that the
   event names.

In TypeScript, `getMultisigEventsFromTransaction(transaction)` does steps 2 to 4 for a
`getTransaction` response (`encoding: "json"`).

The signer check is the proof of the event. Only the program can sign for its multisig and
program config PDAs. Do not trust a `log_event` from a different program ID or with a different
signer.

### 12.5 Cost and limits

- Each event is one more CPI. Execute instructions emit 2 to 4 events.
- An emitting instruction is one CPI level deeper. If your program calls 4r at the maximum CPI
  depth, do not add the event account.
- Measured on the local validator: `vault_transaction_execute` with a 1-instruction message
  uses 15,577 CU without events and 19,999 CU with its 2 events (about 2,200 CU for each event).
  The program answers `log_event` in its entrypoint, before Anchor (550 CU for each call).
  Events with large snapshots cost more. Add this to your compute unit limit when you enable
  events.
- Events do not copy the accounts, so they add little heap use. At the default 32 KiB heap,
  `multisig_add_member` works up to about 244 members, with or without events. Larger multisigs
  and transaction buffers over about 5 KB need `ComputeBudgetProgram.requestHeapFrame` (up to
  256 KiB), also without events.
